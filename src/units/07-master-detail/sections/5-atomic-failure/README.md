# 07-5 原子提交失败：保留草稿重试

## 这一节学什么

主从一起提交时，后端通常是**原子**的：整份请求要么全部保存，要么一条都不保存。
失败后前端要保留所有草稿，让用户只改出错的那一处。

## 核心概念

| 现象 | 说明 |
|---|---|
| 后端拒绝整份请求 | 一条都没保存，包括没出错的头和行 |
| 前端草稿 | 所有头、所有行的修改都保留，`dirty` 仍为 true |
| 原因 | 在 `feedback.submitFailed` 里记下，catch 里显示 |

失败时**不要**：
- `reset()`：撤销所有修改
- `query()`：用后端数据覆盖所有草稿

## 看样例

改角色名、把一条权限说明改成 `FAIL`，保存：提示失败原因，两处改动都在；把 `FAIL` 改掉再保存，成功。

## 练习

记下原因、去掉覆盖草稿的隐患（2 个 TODO）。

## 验收

- [ ] 改员工姓名、把某条技能编码改成 `FAIL`，保存：提示里有后端原因
- [ ] 失败后姓名和技能的改动都还在
- [ ] 把 `FAIL` 改成 `SKILL_X` 再保存：成功

如果后端不是原子的（成功的部分保存了、失败的部分没保存），前端应该怎么处理状态？为什么原子更简单？
